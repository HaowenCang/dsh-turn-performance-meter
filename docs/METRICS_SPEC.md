# Metrics Specification

This file is normative. If code, screenshots, or comments conflict with it, this file wins until deliberately amended.

## 1. Statistical scope

A metric card belongs to one DSH `turn`. A turn may contain multiple steps, model attempts, retries, and tool calls.

The completed values are ratios of turn-level sums, never arithmetic means of per-step/per-attempt TPS values.

## 2. Content classes

### 2.1 Reasoning output

Generated content from non-empty `reasoning-delta` chunks.

### 2.2 Non-reasoning model output

Generated content from:

- non-empty `text-delta` chunks;
- non-empty `tool-call-delta.argumentsDelta` chunks.

Tool-call arguments include shell commands, PowerShell, source code, write-file body, edit patch/diff, structured JSON and any other argument emitted by the model.

### 2.3 Excluded tool results

Never count the following as model output:

- shell/stdout/stderr returned by a tool;
- file contents returned by read/search tools;
- API/MCP result payloads;
- tool error text generated by the tool/runtime.

If such content is sent back to a later model invocation, it belongs to that invocation's input context, not output.

## 3. Authoritative token totals

DSH `TokenUsage.outputTokens` is provider output and may include `reasoningTokens`. DSH's documented contract states that `reasoningTokens`, when present, is already included in `outputTokens`.

For one attempt with both counters:

```text
reasoningTokens_exact = reasoningTokens
outputTokens_exact    = outputTokens - reasoningTokens
allGenerated_exact    = outputTokens
```

Never compute `outputTokens + reasoningTokens`.

For a turn with complete usage on all contributing attempts:

\[
N_{generated}=\sum_i N_{output,i}
\]

If every contributing attempt also reports `reasoningTokens`:

\[
N_{reason}=\sum_i N_{reason,i}
\]

\[
N_{nonreason}=\sum_i (N_{output,i}-N_{reason,i})
\]

If any contributing attempt lacks authoritative usage, the exact turn aggregate is not complete. Degrade quality; do not silently treat missing usage as zero.

### 3.1 Per-phase magnitudes for display (frozen in Phase 4)

The card publishes a per-phase token magnitude for each of the two phases. Its provenance depends on what the provider reported, and the published pair is always reconciled with the published total:

| Provider evidence | Published reasoning / output magnitudes | Quality |
|---|---|---|
| `outputTokens` **and** `reasoningTokens` on every contributing attempt | the provider counters | `exact` |
| `outputTokens` on every contributing attempt, no `reasoningTokens` | the anchored allocation of the authoritative total: `calibrateAttemptSamples` rescales each attempt's phase weights so its phases sum to that attempt's total, and the turn sums those allocations; the output phase absorbs any rounding residual | `estimated` (`partial` when only some attempts reported usage) |
| no provider usage at all | the raw phase shape weights | `unavailable` quality; a rate derived from them is `estimated` |

A phase with no evidence at all is `null` and renders `—`; it is never shown as `0`. This is what makes `phaseSplitQuality === estimated` an *approximate division of a known total* rather than a free-floating estimate, and it is why the card can state a rate for routes that never report `reasoningTokens` while still marking it `≈`.

## 4. TTFT

Turn TTFT is defined once:

\[
TTFT=t_{first\ generated\ delta}-t_{turn/start}
\]

The first generated delta may be reasoning, visible text, or tool-call arguments. Empty deltas do not stop the TTFT clock.

Later LLM calls after tools do not redefine the turn TTFT. Per-attempt first-token latency may be retained internally for diagnostics but is not the primary fourth-column value.

## 5. Tool latency

For each tool call:

\[
T_{tool,i}=t_{result,i}-t_{call,i}
\]

Store at least `callId`, `name`, `startMs`, `endMs`, `status`, and parent id if DSH exposes one.

Two aggregate values are required:

```text
toolWorkMs = Σ completed individual durations
toolWallMs = measure(union of all completed tool execution intervals)
```

`toolWorkMs >= toolWallMs`. They are equal when calls never overlap. The user-facing compact card should normally display `toolWallMs`; detail/debug information can expose `toolWorkMs`.

**Live tool timer (frozen in Phase 3).** The compact live pill's tool figure is the wall-clock duration of the
**current continuous tool-activity episode**: the start boundary of the open union interval of running calls. A call
that starts while others are running joins their episode (the episode keeps the earlier start even after the first call
settles); an episode ends only when the last running call settles, and a call arriving after a quiet gap opens a new
episode. The live timer is therefore never `Σ(active call durations)` and never bridges a gap between episodes.

## 6. Live TPS

Live TPS is a trailing one-second window for the **currently active model attempt**, not a turn average:

\[
TPS_{live}(t)=\frac{N(t-1000\,ms,t]}{1\,s}
\]

Implementation requirements:

- window length: 1000 ms;
- UI refresh target: 100–250 ms, independent from chunk frequency;
- reset at every new model attempt;
- while no model attempt is streaming (tool running or waiting for next model), do not keep displaying a stale TPS as if current;
- live TPS is normally `estimated` unless an exact streaming tokenizer/count is available.

**Warm-up contract (frozen with test in Phase 3).** While the active attempt has been observed for less than the full
window length, the value counts exactly the samples observed since the window opened and still divides by the full
1000 ms. It therefore ramps up with observed evidence and never extrapolates a full-second rate that has not been
measured; a new attempt's reset restarts warm-up from an empty window. Asserted by the `warm-up` test in
`test/sliding-window.test.js`.

**Approximation is mandatory.** Live TPS carries `≈` in every rendering (§11.4/§11.5): no live value may be presented
without the approximate marker.

A model-aware exact tokenizer may replace the fallback estimator if verified for the active provider/model. Do not assume GPT/tiktoken tokenization for DeepSeek or other providers.

## 7. Completed turn TPS

Completed turn-level reasoning TPS:

\[
TPS_{reason,turn}=\frac{\sum_i N_{reason,i}}{\sum_i T_{reason,i}}
\]

Completed turn-level non-reasoning output TPS:

\[
TPS_{output,turn}=\frac{\sum_i N_{nonreason,i}}{\sum_i T_{output,i}}
\]

Never compute:

\[
\frac{TPS_1+TPS_2+\cdots+TPS_n}{n}
\]

Tool time and between-call waiting time are excluded from both denominators.

### Phase-duration policy

DeepSeek must implement and test one deterministic policy for phase duration using timestamped generated deltas. Required properties:

1. pre-first-token TTFT is excluded;
2. tool/inter-attempt time is excluded;
3. intra-stream stalls between generated deltas remain included because they reflect model delivery stability;
4. reasoning and output durations must not double-count the same interval;
5. one-delta and zero-duration edge cases must not produce division by zero or fake infinite TPS.

**Implemented policy.** Within one attempt, sort non-empty generated deltas by timestamp; attribute each inter-delta interval to the phase of the *earlier* delta. The trailing interval — from the last non-empty model-producing delta to the attempt's durable settlement — is **not** charged to any phase.

**Frozen on measured evidence (Phase 2).** The trailing-interval branch was decided by measuring ten real attempts across `fixtures/dsh-turns/`:

| Observation | Measurement |
|---|---|
| tail (settlement − last model-producing delta) | 3 ms – 260 ms, mean 37.9 ms |
| gap from the stream's own `finish` chunk to the settlement | 1 ms – 8 ms |
| longest attempt (33 849 ms of generation) | 18 ms tail |
| interrupted attempt (no `finish` chunk) | 260 ms tail |

Every normally completed attempt ends its recorded stream with the model's own `finish` chunk, and the settlement lands 1–8 ms after that chunk. The settlement therefore trails the *stream*, not the decode loop, and the remaining interval is host commit and prefix-finalization work. That is also why the tail does not scale with generation length: a 33.8 s attempt has an 18 ms tail, while an interrupted 3.8 s attempt has a 260 ms tail because it must finalize a delivered prefix with no `finish` chunk to bound it.

Charging the tail would mix host overhead into the decode denominator for every attempt, and would matter most exactly where the numbers are least stable (short attempts: the tail is 17 % of an 18 ms span). Omitting it slightly under-counts generation time for very short final tails; that error is bounded by the measured tail and is the smaller of the two distortions. Reproduce with `node dev/measure-generation-tail.mjs`; assert with `test/generation-tail.test.js`.

## 8. Completed curve

The curve is mandatory but visible only in the completed card's hover/focus alternate view.

### 8.1 X-axis

Use compressed model-generation time. For every attempt with generated deltas:

- attempt-local x=0 at first non-empty generated delta;
- preserve wall-time distances between deltas inside the attempt;
- append the next attempt immediately after the previous attempt's last generated delta;
- allocate no x-axis width to tools, inter-attempt waits, or next-call TTFT.

The curve is therefore a model-throughput diagnostic, not an end-to-end turn timeline.

### 8.2 Y-axis and window

Use the same conceptual one-second trailing TPS window as the live meter, sampled for rendering every ~250 ms on the compressed active clock. Implement rendering density independently from the underlying sample collection so the SVG remains bounded for long turns.

### 8.3 Calibration

Stream deltas do not generally expose exact per-delta token counts. Use a two-stage process:

1. capture timestamp + phase + a token-shape weight for every generated delta;
2. when authoritative usage arrives, scale each phase's weights so the sum equals its exact phase token total.

If an attempt reports `outputTokens` and `reasoningTokens`, reasoning and non-reasoning output curves can each be calibrated separately. The curve's local shape remains an estimate while its phase integral is anchored to exact aggregate counts; the axis that describes this is `temporalShapeQuality = reconstructed` (§11), and `curve.quality` carries that value.

If `reasoningTokens` is absent, do not claim the reasoning/output split is exact. The whole-attempt integral is still anchored to the authoritative `outputTokens` by one common factor, so the curve shape remains usable; `phaseSplitQuality` in that case is `estimated`, and the two phase series must be presented as one approximate division of an exact total rather than as two measured curves.

## 9. Peak TPS

`peakTps` is the maximum rendered rolling-window value among both reasoning and output series after final calibration, using the same window and sampling cadence documented above. Label it as peak of the displayed/calibrated series, not as a provider-certified instantaneous maximum. Because the window is a shape estimate, the peak inherits `temporalShapeQuality` and never exceeds `reconstructed`.

## 10. Total elapsed time

Turn elapsed time:

\[
T_{turn}=t_{turn/end}-t_{turn/start}
\]

This **does** include model waits and tool execution because it describes user-perceived turn duration. It is a secondary line, not a TPS denominator.

## 11. Metric quality

A single label must not describe a whole curve. The same turn routinely has an exactly known token total, a reasoning/output split the provider never reported, and a timing shape that is reconstructed from delta weights. Collapsing those into one word forces at least one of them to be misreported, so quality is tracked on **three independent axes**.

### 11.1 Levels

| Quality | Meaning |
|---|---|
| `exact` | authoritative aggregate provider counter / exact durable boundary |
| `calibrated` | curve/local allocation adjusted to exact aggregate total |
| `reconstructed` | exact phase integrals anchored to authoritative totals, on a local shape that remains an estimate |
| `partial` | some contributing attempts were authoritative and some were not |
| `estimated` | heuristic/tokenizer estimate without authoritative local count |
| `unavailable` | insufficient evidence |

`partial` and `reconstructed` are additions to the four originally frozen levels, not replacements. `partial` distinguishes "1 of 3 attempts reported usage" from a wholesale estimate; `reconstructed` distinguishes an anchored curve from a rough one.

### 11.2 Axes and ceilings

| Axis | Answers | Strongest reachable value |
|---|---|---|
| `tokenTotalQuality` | how well the *total* generated tokens are known | `exact` |
| `phaseSplitQuality` | how well that total is divided into reasoning vs non-reasoning output | `exact` |
| `temporalShapeQuality` | how well the *timing* of generation is known | `reconstructed` |

`temporalShapeQuality` can never reach `exact`. DSH attaches no token count to a delta, so every curve point carries a shape weight; even with exact timestamps and exact phase integrals, the local magnitude is an estimate. The ceiling is enforced in `src/core/quality-model.js`, not by convention.

`phaseSplitQuality` is additionally capped by `tokenTotalQuality`: a split cannot be better known than the total it divides.

### 11.3 Derivation

| Evidence | tokenTotalQuality | phaseSplitQuality | temporalShapeQuality |
|---|---|---|---|
| authoritative `outputTokens` and `reasoningTokens` on every contributing attempt, durable timestamps | `exact` | `exact` | `reconstructed` |
| authoritative `outputTokens` on every contributing attempt, no `reasoningTokens` | `exact` | `estimated` | `reconstructed` |
| authoritative usage on some contributing attempts only | `partial` | at most `estimated` | `reconstructed` |
| no provider usage at all, durable timestamps | `unavailable` | `unavailable` | `estimated` |
| no provider usage, live observation only | `unavailable` | `unavailable` | `estimated` |
| a contributing attempt carried no delta timestamp, or its shape is not anchored to a total | unchanged | unchanged | `estimated` |
| no contributing attempt at all | `unavailable` | `unavailable` | `unavailable` |

### 11.4 UI rules

- `exact`: normal number. This is the **only** level that suppresses the approximate marker.
- `reconstructed`, `calibrated`, `partial`, `estimated`: prefix `≈` or expose an explicit estimated indicator. A live value is always in this group, because no per-delta provider count exists.
- `unavailable`: `—`.
- never silently coerce `unavailable` to zero.

The three axes travel with the settled snapshot as `quality`, so a renderer never has to re-derive them:

```js
snapshot.quality = {
  tokenTotalQuality, phaseSplitQuality, temporalShapeQuality,
  approximateTokenTotal, approximatePhaseSplit,
  displayTokenTotal, displayPhaseSplit,   // 'exact' | 'approximate' | 'unavailable'
  notes,                                   // human-readable reasons, already worded
}
```

### 11.5 Live values

Live TPS is `estimated` unconditionally: it is a shape weight inside a one-second window, anchored to nothing until the attempt settles. A future model-aware exact tokenizer would change that, and would have to be verified for the active provider/model route first (see §6).

### 11.6 Provider/stream consistency guard

Provider aggregate usage and stream phase evidence must agree before a split may be claimed as `exact`. The guarded
conflict (frozen in Phase 3, tested at unit, aggregate and fixture level):

> an attempt whose stream contains at least one **non-empty `reasoning-delta`** while its provider usage explicitly
> reports **`reasoningTokens === 0`**.

When the conflict fires:

1. `tokenTotalQuality` is untouched — the authoritative `outputTokens` remains the total's basis;
2. `phaseSplitQuality` is downgraded to at most `estimated`, however many attempts reported the counter;
3. the legacy `splitQuality` label degrades with it, and derived rates stop claiming `exact`;
4. every conflict is reported in `consistencyIssues` and as a `quality.notes` entry — never silently ignored, never
   resolved by discarding the stream evidence.

A `reasoningTokens === 0` report **without** reasoning stream evidence (tool-argument-only attempts, e.g. `t4` step 2)
is consistent and keeps an `exact` split.

## 12. Status

Final card status must distinguish at least:

- `completed`
- `interrupted`
- `errored`

An interrupted prefix may still have observed throughput. Status describes settlement, not whether metrics exist.

`turn/end.reason` maps as follows (verified against the local `0.1.5-rc.2` `TurnEndReasonMap`, recorded in `docs/IMPLEMENTATION_LOG.md`):

| `turn/end.reason.kind` | status | note |
|---|---|---|
| `completed` | `completed` | — |
| `aborted` | `interrupted` | carries the cancellation cause (`user`, `parent`, `hook`, `disposed`, `legacy`) |
| `interrupted` | `interrupted` | crash-orphaned turn closed after the fact |
| `blocked` | `errored` | — |
| `error` | `errored` | carries the structured `LlmFailure` |
| `max-tokens` | `completed` | truncated; the ceiling is noted on the secondary line |
| unrecognized | `errored` | reported with `statusKnown: false`; a future reason kind must never be mapped to a known cause |

## 13. Evidence sources

Two DSH planes feed every metric, and neither may be substituted for the other:

| Plane | Source | Role |
|---|---|---|
| durable | `session/event` — `turn/start`, `step/*`, `assistant/message`, `assistant/attempt`, `tool/call`, `tool/result`, `turn/end` | authoritative boundaries, provider usage, replay-safe reconstruction including the timed delta stream |
| transient | `agent/assistant-stream` frames, or the client-folded `assistant/live-chunk` rows | live-only observation: the in-flight window, in-flight sample timestamps, attempt identity |

Rules that follow from the split:

1. every metric must be reconstructible from the durable plane alone once a turn has settled; the transient plane may only ever add freshness, never correctness;
2. attempt identity (`attemptId`) exists only on the transient plane — DSH never writes it to the durable log — so a durable reconstruction keys attempts by their settlement sequence, and no statistic may depend on the identity string;
3. provider usage has exactly two authoritative carriers, `assistant/message.usage` and an in-stream `StreamChunk{type:'usage'}`. Either may be used; both must never be added;
4. `reasoningTokens`, when present, is already inside `outputTokens`. The two counters are never summed, and non-reasoning output is always `outputTokens - reasoningTokens`;
5. tool results never enter the output accounting path. A `tool/result` payload, a shell's stdout, a file body returned by a read tool or an API response are inputs to a later model call, not model output.

The equivalence of the two planes for a settled turn is a tested property, not an assumption: `test/dsh-equivalence.test.js` drives both paths for every recorded fixture and asserts agreement on phase segmentation, token totals, phase durations, compressed chart coordinates, peak TPS, tool durations and accounting, TTFT and the quality axes.

### 13.1 Attempt settlement semantics (audited against local 0.1.5-rc.2)

Three concepts are kept strictly separate on every `AttemptRecord`; no field carries all three:

| Concept | Field | Values |
|---|---|---|
| durable settlement type | `settlementKind` | `message` (`assistant/message`) · `attempt` (`assistant/attempt`) · `none` (no durable settlement) |
| surface visibility | `surfaceCommitted` | whether a model-visible assistant message exists |
| execution outcome | `attemptOutcome` | `committed` · `interrupted` · `failed` · `retried` · `cancelled` · `stream-error` · `abandoned` · `unknown` |

Evidence rules, verified in the installed runtime:

- `assistant/message` is the surface settlement; its `interrupted: true` marker yields outcome `interrupted`;
- `assistant/attempt` is a **durable settlement without a surface message** ("failed, retried, cancelled, or
  stream-error attempt that reached settlement") — it is *not* an abandonment, and its outcome stays `unknown` unless
  a durable `llm/retry` naming the same turn/step and preceding only this attempt proves `retried`;
- `abandoned` comes **only** from the transient `AssistantStreamFrame.end.outcome.kind === 'abandoned'`
  ("live abandonment without one [durable settlement]");
- anything the durable evidence cannot derive stays `unknown`. Nothing is guessed.

### 13.2 Reload reconstruction of the completed card (frozen in Phase 4)

A card must be reachable from a window that contains **only** the durable plane. Two consequences are normative:

1. The window does not need to carry `turn/start` for the turn to be *measured*; it needs it for TTFT and elapsed time. A settlement that arrives with no matching in-memory turn record therefore restores its attempt from the stream embedded in the durable row (`attemptFromDecoded`), derives `firstTokenMs` as the earliest restored sample timestamp, and can still report TTFT. When the window has lost `turn/start` altogether, `ttftMs` and `turnElapsedMs` are `null` and render `—`; no start time is fabricated, because a fabricated one would corrupt both values.
2. When the window still holds transient rows for the same attempt, the durable settlement is correlated to that attempt by its `(turn, step)` **only if exactly one unsettled attempt matches**. With two candidates the correlation is unprovable, and the durable row is restored as its own attempt rather than attached to a guess.

The card a reload produces must equal the card the live session produced. This is tested per recorded fixture in `test/completed-lifecycle.test.js` (durable-only window versus live-observed window, compared through the view model) and, for the underlying metrics, in `test/dsh-equivalence.test.js`.
